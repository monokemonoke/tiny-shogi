## TL;DR

- 4x4ミニ将棋をブラウザで遊べるようにし、AIは「その場探索」ではなく「事前計算DB参照」にした
- フロントは Three.js + TypeScript、APIは Cloudflare Pages Functions、局面DBは D1
- 局面ハッシュを正規化（180度回転同値）して、DBサイズと参照効率を現実的にした

## はじめに

先に言うと、このAIはかなり強いです。  
というか、DBに入っている範囲では最善手しか返しません。

「将棋AIをWebで遊べるようにしたい」という気持ちで作り始めたんですが、  
途中で「小さい将棋なら完全解析に寄せたほうが面白いのでは？」に振り切りました。

結果として、次のような構成になりました。

- 対局UI: `game.ts` / `game.html`
- 解析API: `functions/api/analyze.mjs`
- 解析データ生成: `src/main.rs`
- 配信基盤: Cloudflare Pages + D1

## なぜこの構成にしたか

要件はシンプルでした。

1. ブラウザですぐ遊べること
2. AI応答を軽くすること
3. 個人開発でも運用コストが重くならないこと

その結果、推論をリアルタイムで回すのではなく、  
Rustで事前生成した局面評価をD1に置いて、Functionsから参照する形にしました。

「重い処理はオフライン」「本番は参照だけ」に分けると、体感がかなり安定します。

## ルール実装（4x4ミニ将棋）

このアプリで実装しているのは、王・金・角・馬（角の成り）だけの4x4将棋です。  
小さい盤面でも、実装で厄介なのは普通の将棋と同じで以下でした。

- 擬似合法手と合法手の分離
- 自玉が取られる手の除外
- 持ち駒を打つ処理
- 角の成り（任意成り）

`game.ts` 側では、まず駒の動きとして成立するかを判定し、  
その後に盤面をシミュレーションして「王手放置」を弾いています。  
API側（`functions/api/analyze.mjs`）でも同じルール体系で次局面生成を行い、評価参照に繋げています。

## “Perfect AI感”の肝: 局面ハッシュの正規化

このプロジェクトで一番効いたのは、局面キーの扱いです。

同じ局面でも「先後を反転して180度回転」しただけの同値形が多く出ます。  
そこで通常ハッシュと反転ハッシュを両方計算して、`min(hash1, hash2)` を採用しています。

これで次が改善しました。

- DBに保存する状態数の削減
- キャッシュ効率の改善
- 実装上の「同じ局面なのに別キー問題」の回避

要するに、「ゲームの対称性をデータ構造側で先に使い切る」方針です。

## 体験設計: 厳密値をそのまま見せない

厳密値が `Win/Lose/Draw` で取れても、それだけだとプレイ体験が硬いです。  
そこで手数情報（何手勝ち/何手負け）をUI表示にマップして、勝率風の見え方を作っています。

- 例: `先手 13手勝ち`
- 例: `先手 72%`

厳密な意味での確率ではないですが、  
「今の手がどれくらいマズいか/良いか」はかなり直感的になります。

## 開発とデプロイ

このリポジトリでは、次のスクリプトで回しています。

- 開発: `npm run pages:dev`
- デプロイ: `npm run pages:deploy`
- ローカルD1準備: `npm run db:setup`

Cloudflare Pages Functions と静的配信を同じ導線で扱えるので、  
小〜中規模のWebゲームにはかなり合っていました。

## ハマりどころ

実際に詰まったのはこのあたりです。

- フロントとAPIでルールが1文字でもズレると評価が壊れる
- ハッシュ仕様を変えると既存DBの互換が消える
- 厳密値をそのまま出すと、ユーザーには温度感が伝わりにくい

この3つは、仕様の単一化と表示レイヤーの工夫でなんとかしました。
