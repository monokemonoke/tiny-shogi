## このアプリで、人間はAIに勝てる

最初に言っておきたいことがある。

このアプリのAIは、完全解析にもとづいて動いている。すべての局面で最善手を返す。そういう意味では、隙のないAIだ。

それでも、あなたはこのAIに勝てる。

理由は単純で、この4×4ミニ将棋は**先手必勝**だからだ。人間は先手を持つ。正しく指し続ければ、必ず勝てる。AIは後手として最善を尽くすが、それでも負ける。

最近、AIが人間に勝つという話は珍しくなくなった。将棋でも、囲碁でも、チェスでも、AIは人間のトッププロを超えている。完全解析されたゲームであれば、なおさらだ。

だとすれば、こういう問いが浮かぶ。完全解析されていても、人間が正しく指せば勝てるゲームとは、どんな体験になるだろうか。

それを確かめたくて作った。

## なぜどうぶつしょうぎではないのか

完全解析された将棋系ゲームとして、[どうぶつしょうぎ名人](https://mame.github.io/dobutsu-shogi-master/)がある。mameさんが作られたWebアプリで、技術的にも体験設計としても、よくできている。

どうぶつしょうぎは**後手必勝**のゲームだ。だから、あのアプリで人間は絶対に勝てない。それはそれで体験として面白いのだが、「勝ちを学ぶ余地がない」という感覚が残る。

もうひとつ感じることがある。どうぶつしょうぎはよくできたゲームだが、本将棋とは別のゲームだ。盤が3×4マスで、駒は4種類。将棋を指す人間の感覚からすると、少し距離がある。

では、もう少し本将棋に近い構造のゲームが完全解析されたら、どんな印象を受けるだろう。王手・持ち駒・成りといった、将棋らしい要素が残ったまま「完全に解かれた」状況は、将棋を指す人間にとってどう響くのか。

そういう疑問から、4×4の盤面に王・金・角（成ると馬）だけを置いたミニ将棋を題材に選んだ。将棋のコアな要素は残しつつ、局面数が完全解析の届く範囲に収まるサイズだ。

## コーディングエージェントがあったから作れた

もうひとつの動機も書いておく。

3Dモデリングも、Rustでの完全解析エンジンも、以前なら一人では手が届きにくかった。コーディングエージェントが実用的になってきた今、「試みること」のコストが下がった。Three.jsの3D盤面も、後退解析のアルゴリズムも、エージェントと対話しながら進めることができた。

「やってみたかったけど、むずかしそうで後回しにしていたもの」を実際に手を動かして確かめられる時代になってきた。このプロジェクトは、そのことを実感する機会でもあった。

## 完全解析の仕組み: 後退解析

このアプリのAIは、対局中にリアルタイムで先読みをしていない。Rustで事前に計算した「全局面の評価」をDBに格納してあり、ユーザーが手を指すたびにDBを1回引くだけだ。

全局面の評価をどう計算するか。使うのは**後退解析（retrograde analysis）**という手法だ。

まず「詰んでいる局面」——合法手が存在しない局面——を「負け」として確定させる。次に、「一手で負け局面に遷移できる局面」は「勝ち」と確定できる。さらに「すべての遷移先が相手の勝ち局面である局面」は「負け」と確定できる。

これを変化がなくなるまで繰り返す。有限の二人零和完全情報ゲームであれば、この操作は必ず収束する。最終的にすべての局面が Win・Lose・Draw のいずれかに分類される。

実装はRustで行った。`cargo run --release -- all` を実行すると全局面の評価が計算され、SQLiteファイルとして出力される。

## 局面の表現と正規化

4×4の盤面（16マス）に王・金・角・馬が入る。各マスの状態を4bitで表現すると、盤面全体で64bit。持ち駒と手番を加えて、一局面をu128として扱っている。

そこに一つの工夫を加えた。**局面の正規化**だ。

先後を入れ替えて盤面を180度回転させた局面は、元の局面と本質的に同じ構造を持つ。先手から見た「この局面」と後手から見た「同一の局面」は、DBには一つのエントリとして保存できる。

```rust
fn canonical_hash(&self) -> u128 {
    let h1 = self.encode_hash();
    let h2 = self.encode_hash_rotated(); // 180度回転 + 先後反転
    h1.min(h2)
}
```

この正規化によって、DBに格納する局面数はおよそ半分になる。ただし、Rustの解析コードとTypeScript（Cloudflare Functions）のAPIコードが同じ正規化ロジックを持つ必要がある。この整合性の確認には、実装を通じて一番注意を払った部分でもあった。

## 評価値をUIでどう伝えるか

解析結果として得られるのは「Win（n手）」「Lose（n手）」「Draw」という厳密な値だ。しかしこれをそのまま画面に出しても、プレイ感は生まれにくい。

手数情報を評価バーにマッピングした。「現在の局面から最善を尽くした場合に何手で勝負がつくか」を視覚化することで、「今の一手がどれほど影響したか」が直感的にわかるようにした。

数値として確定しているものを、体験として伝えるための変換層だ。

## 構成とデプロイ

| レイヤー | 技術 |
|---|---|
| フロントエンド | Three.js + TypeScript（3D盤面、アニメーション） |
| API | Cloudflare Pages Functions |
| DB | Cloudflare D1（解析結果のSQLite） |
| 解析エンジン | Rust（オフラインで事前実行） |

Cloudflare Pages + D1の組み合わせは、個人開発のWebゲームとして扱いやすかった。静的配信とAPIを同じリポジトリの導線で管理でき、D1は無料枠の範囲で十分に動いた。

```bash
npm run pages:dev     # ローカル開発
npm run db:setup      # ローカルD1の準備
npm run pages:deploy  # 本番デプロイ
```
